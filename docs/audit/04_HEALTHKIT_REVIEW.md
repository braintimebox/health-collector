# 04 — HealthKit review

## Что запрашивается (CONFIRMED, `HealthKitSource.swift:44-66`)

Read-only, восемь проб: HRV SDNN (ms), пульс, пульс покоя, дыхание (count/min), шаги (count),
активная энергия (kcal), сон (`sleepAnalysis`, категория) и тренировки (`HKWorkoutType`).
Сон отправляется **семью типами по стадиям** (`SleepStage.wireType`), а не одним агрегатом.

## Разрешения

- Запрашивается только чтение: `requestAuthorization(toShare: [], read: read)`.
- Статус чтения принципиально не наблюдаем (Apple): приложение об этом говорит честно и не рисует
  «Connected». `authorizationStatus` используется только там, где он осмыслен (запись) — сейчас нигде,
  что корректно для read-only.
- `enableBackgroundDelivery` вызывается для каждого типа, но его результат **игнорируется**
  (`:115-118`) и нигде не отображается: диагностика не может ответить «фон работает?».

## Механика

| Механизм | Реализация | Оценка |
|---|---|---|
| Anchored queries | `HKAnchoredObjectQuery` + `HKQueryAnchor` в `AnchorStore` | корректно |
| Курсор на тип | отдельный ключ на каждый тип (включая стадии сна) | корректно |
| Удаления | `deletedObjects` → `DeletedRecord` → tombstone на сервере | корректно |
| Provenance | `sourceRevision.source.name/bundleIdentifier` в каждой записи | корректно |
| Observer | `HKObserverQuery` + `completion()` во всех ветках | корректно (иначе 3 промаха отключают доставки) |

## Проблемы

1. **Блокирующее чтение.** `fetch`/`fetchWindow` ждут `DispatchSemaphore` до 30 с на тип
   (`:158`, `:204`). Вызываются из `Collector` внутри `queue.async` (`Runtime.swift:211`) — то есть на
   serial-очереди `qos: .utility`, а не на главном потоке: интерфейс не замерзает, но очередь стоит до
   4 минут на восьми типах, и «статус не обновляется» неотличимо от «всё сломалось». (CONFIRMED;
   формулировка «блокирует UI» была бы неверной — главный поток не затронут.)
2. **Отсутствие наблюдаемости фона.** Нет ни одного поля «background delivery: enabled/denied», хотя
   именно это первое, что нужно при разборе «данные не приходят».
3. **Нет повторной обработки событий observer.** Каждое пробуждение просто запускает общий `syncNow`;
   дедупликация спасает, но серия пробуждений даёт серию полных проходов. (POTENTIAL: нагрузка не
   измерялась.)

## Рекомендации

- Перевести чтение на `async` (`HKAnchoredObjectQueryDescriptor` / continuation без семафора) и
  ограничить параллелизм: один тип за раз, таймаут на уровне задачи.
- Сохранять результат `enableBackgroundDelivery` в состояние и показывать в Advanced как
  «enabled / denied / unknown» — честно, без догадок.
